# 2026-05-05 工作记录

## 自启动可靠性改进

### 问题
- 用户反馈真机开机自启动失败（BOOT_COMPLETED 被国产 ROM 拦截）
- 日志显示 Hook 侧 loadAllConfig 全部 size=0（system_server 读不到 App 私有目录文件）

### 修复内容

#### 1. BootReceiver 增加多个触发 Intent（Manifest + Java）
- 新增 `ACTION_USER_PRESENT`（用户解锁屏幕，最可靠）
- 新增 `ACTION_TIME_SET`、`ACTION_TIMEZONE_CHANGED`（开机时常触发，作为兜底）
- 保留 `BOOT_COMPLETED` + `QUICKBOOT_POWERON`
- 移除无用的 `<category DEFAULT />`

#### 2. Hook 侧移除无效操作
- 删除 5s/8s 延迟中的 `loadAllConfig()`（system_server 读不到文件）
- 删除 `scheduleConfigRetry()`
- Hook 侧只负责注册广播接收器，被动等待 App 推送配置

#### 3. ConfigSyncService 方案（两版迭代）

**v1（已废弃）**：Hook 侧用 `startService()` 拉起 ConfigSyncService
- system_server 跨进程启动 App Service → App 读文件发广播
- 问题：Service 能启动但广播推送不可靠（Hook 侧收不到广播）

**v2（当前）**：BootReceiver 启动 ConfigSyncService 前台服务
- BootReceiver 收到广播 → `startForegroundService(ConfigSyncService)`
- 前台服务比 `goAsync()` 更可靠（goAsync 最多 10 秒，我们需要 12 秒）
- Service `onCreate` 中调 `startForeground()` + 通知
- `onStartCommand` 中子线程延迟 12s/15s 发配置广播
- Manifest：`exported="false"` + `foregroundServiceType="specialUse"`
- 权限：`FOREGROUND_SERVICE` + `FOREGROUND_SERVICE_SPECIAL_USE`
- BootReceiver 加 60 秒防抖（防止 USER_PRESENT 多次触发）
- 完成后 `stopForeground()` + `stopSelf()` 自动退出

#### 4. 日志区分
- WriteHook.java 中 4 处日志加上 `WriteHook` 前缀

### 配置同步时机
```
1. BootReceiver 自启动 → ConfigSyncService 前台服务（12s/15s 广播推送）
2. 打开 App（MainActivity.onCreate → sendFullConfigBroadcast）
3. 配置改变时（保存写入/读取权限和规则时发广播）
```

### 开机时序
```
t=0:    Hook 加载（注册 Hook，不加载配置）
        └─ postDelayed 5s, postDelayed 8s

t=5s:   tryRegisterReceiver("延迟5s")
        └─ 成功 → 等待 App 广播推送配置

t=8s:   tryRegisterReceiver("延迟8s")（兜底）

BootReceiver 收到开机/解锁/时间变化广播（任一触发）：
  └─ 启动 ConfigSyncService 前台服务（显示通知）
  └─ 12s 后发配置广播 → Hook 侧收到 ✅
  └─ 15s 后发第二次广播（兜底）✅
  └─ 更新通知"剪贴板保护服务已启动"
  └─ stopSelf() 退出

用户复制时：ensureInitialized() → 确保广播接收器已注册 → 保守放行或拦截
```

### 配置同步 v6：Hook 侧 ContentProvider 主动拉取兜底

#### 问题
- 用户确认已开启自启动白名单，但 BootReceiver 在真机仍然不触发
- 国产 ROM 对第三方 App 的 BOOT_COMPLETED/USER_PRESENT 广播选择性拦截
- 自启动白名单 ≠ 广播必达，部分 ROM 只保证进程不被杀

#### 方案
在 `ensureInitialized()` 中增加 ContentProvider 主动拉取逻辑：
- 当广播通道没有推送配置（`sWriteLoaded == false`）时，主动通过 `ContentProvider.call()` 拉取
- 只尝试一次（`sProviderFetchAttempted` 标记），避免每次复制都发起跨进程调用
- ContentProvider 在 user unlock 后可用，首次复制时通常已经可用
- 使用 `clearCallingIdentity()` 绕过 uid 校验
- 会产生 `FLAG_ONEWAY` 警告但不影响功能

#### 改动文件
1. **PermissionCache.java**：新增 `fetchConfigFromProvider(Context)` 方法，通过 ContentProvider.call() 拉取 write/read blocklist，新增 `Uri`/`Bundle` import
2. **WriteHook.java**：`ensureInitialized()` 在配置未加载时调用 `fetchConfigFromProvider()` 兜底，新增 `sProviderFetchAttempted` 标记

#### 更新后的配置加载策略（优先级）
```
1. 广播推送（BootReceiver/打开App/保存配置）→ 最快最可靠
2. ContentProvider 主动拉取（首次复制时兜底）→ 只尝试一次
3. 保守放行（前两条都失败时）→ 不误拦
```
