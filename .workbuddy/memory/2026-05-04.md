# 2026-05-04 工作记录

## 修复：广播 RECEIVER_NOT_EXPORTED 导致 Hook 侧收不到 App 广播（最关键修复）

### 问题根因
`PermissionCache.registerRefreshReceiver()` 在 Android 14+ 使用了 `Context.RECEIVER_NOT_EXPORTED` 注册广播接收器。
广播发送方是普通 App 进程，接收方在 system_server 进程——**跨进程广播被 RECEIVER_NOT_EXPORTED 完全屏蔽**，
导致无论 BootReceiver 还是 MainActivity 发的广播，Hook 侧都收不到，writeBlockSet 始终为 0。

### 修复
改为 `Context.RECEIVER_EXPORTED`，允许接收跨进程广播。

### 同时修改
- BootReceiver 改为收到开机广播立即发送（不延迟），3s 后发第二次兜底
- 之前是 12s/15s 延迟发送

## 修复：写入 Hook 开机后不生效问题

### 问题根因
时序竞争：广播接收器注册太晚 vs BootReceiver 发广播太早。

- 旧逻辑：Hook 加载后 postDelayed(8s) 才注册广播接收器
- BootReceiver：开机广播后等 3s 就发 sendFullConfigBroadcast
- 结果：t=6s 广播发出时，t=8s 才注册接收器 → 广播丢失 → blocklist 为空 → 全部放行

### 修复内容

**WriteHook.java**：
- 新增 `tryRegisterReceiver(tag)` 静态方法，封装注册逻辑
- Hook 成功后立即调用 `tryRegisterReceiver("立即")`，不等待 8s
- 8s 后的 postDelayed 改为补注册（兜底）+ 无条件重新加载文件

**BootReceiver.java**：
- `INITIAL_DELAY_MS`：3s → 12s（确保 Hook 侧 8s 补注册已完成）
- 新增 `SECOND_BROADCAST_DELAY_MS = 3000L`：第一次广播发出后 3s 再发一次（兜底）

### 新时序
```
t=0:   Hook 加载 → 立即 tryRegisterReceiver
t=0~3: 可能注册成功（AMS 就绪时）
t=8:   补注册广播接收器（兜底）+ 重新加载文件
t=12:  BootReceiver 第一次发广播 → Hook 侧一定已注册完毕
t=15:  BootReceiver 第二次发广播（兜底）
```

## 2026-05-04 第二次修复：App 内更改配置无效

### 根本原因
`PermissionProvider.sendBlocklistBroadcast()` 和 `sendFullConfigBroadcast()` 中有以下判断：
```java
if (!writeBlocklist.isEmpty()) {
    intent.putStringArrayListExtra("write_blocklist", new ArrayList<>(writeBlocklist));
}
```
当用户把所有应用设为"放行"（不拦截）并保存时，`writeBlocklist` 为空列表 → `if` 条件为 false → intent 里没有 `write_blocklist` key → Hook 侧收到广播后 `intent.hasExtra("write_blocklist")` 为 false → **跳过 updateFromWriteBlockList → 旧的 sWriteBlockSet 没有被清空**。

### 修复内容（PermissionProvider.java）
`sendBlocklistBroadcast` 和 `sendFullConfigBroadcast` 中，去掉 `if (!list.isEmpty())` 判断，无论 blocklist 是否为空都调用 `intent.putStringArrayListExtra(key, list)`，确保 Hook 侧永远能感知数据变化（包括清空）。

## 2026-05-04 第三次修复：Android 15 真机 Hook 完全不生效

### 根本原因
Android 14 起（API 34+），Google 将系统剪贴板服务从 `ClipboardService` **重命名**为 `ClipboardManagerService`。用户真机为 Android 15，代码中的三个候选类名全部不存在，`findClass` 抛 `ClassNotFoundException` 被 `catch (Throwable ignored) {}` 静默吞掉。

### 修复内容（WriteHook.java + ReadHook.java）

**候选类名扩展**（Android 14+ 兼容）：
```java
// Android 14+ (API 34+)
"com.android.server.clipboard.ClipboardManagerService",
"com.android.server.clipboard.ClipboardManagerService$Impl",
"com.android.server.clipboard.ClipboardManagerService$BinderService",
"com.android.server.clipboard.ClipboardManagerService$ClipboardImpl",
// Android 13 及以下 (API 33-)
"com.android.server.clipboard.ClipboardService",
"com.android.server.clipboard.ClipboardService$ClipboardImpl",
"com.android.server.clipboard.ClipboardService$BinderService",
```

**异常日志增强**：`catch (Throwable ignored) {}` → `catch (Throwable t) { Log.w(TAG, "候选类未找到: " + className, t); }`

## 2026-05-04 第四次修复：Hook 成功后初始化代码导致 handleLoadPackage 崩溃

### 背景
用户反馈：之前的版本在 Android 15 真机能 Hook 成功（只是需要手动打开一次 App），但修改后的版本 Hook 完全不生效。
说明**不是** Android 14 类名变更的问题（之前的版本类名就是对的）。

### 根本原因
今天的修改在 `hookClipboardService` 中 `XposedBridge.hookMethod()` 之后、`return` 之前添加了大量初始化代码：
- `tryRegisterReceiver("立即")`
- `PermissionCache.loadWriteBlockSet()` / `loadReadBlockSet()`
- `ContentRulesManager.loadRules()` / `loadReadRules()`

如果这些初始化代码中**任何一行**抛出未捕获的异常，会导致 `handleLoadPackage` 整体失败。LSPosed 检测到模块异常后标记为失败状态。

同时 `ContentRulesManager.loadRules()` 和 `loadReadRules()` 方法内部也缺少 try-catch 保护。

### 修复内容

1. **WriteHook.java**：
   - `hookClipboardService` 中 Hook 成功后的所有初始化代码用 try-catch 包裹
   - Handler 回调中的延迟初始化也用 try-catch 包裹
   - `handleLoadPackage` 最外层加 try-catch 作为最后防线

2. **ReadHook.java**：
   - `handleLoadPackage` 最外层加 try-catch 保护

3. **ContentRulesManager.java**：
   - `loadRules()` 方法整体加 try-catch，异常时 `sRulePatterns.clear()` + `sLoaded = false`
   - `loadReadRules()` 方法整体加 try-catch，异常时 `sReadRulePatterns.clear()` + `sReadLoaded = false`

### 经验教训
**Xposed 模块的 `handleLoadPackage` 中，`XposedBridge.hookMethod()` 之后的任何代码都必须用 try-catch 包裹！** 即使 Hook 已成功注册，如果后续初始化代码抛异常，LSPosed 会禁用整个模块。

## 日志迁移到 LSPosed Manager

### 动机
用户反馈 `adb logcat -s ClipboardGuard.Hook ...` 过滤后无输出，Hook 侧日志无法通过 logcat 查看。

### 方案
创建 `XLog.java` 工具类，封装 `XposedBridge.log()`，提供 `d/i/w/e` 静态方法。
所有 12 个 Java 文件的 `Log.x()` / `android.util.Log.x()` 统一替换为 `XLog.x()`。

日志格式：`[级别][标签] 消息`，例如 `[I][ClipboardGuard] Hook成功: xxx`

### 修改文件
XLog.java（新建）、WriteHook、ReadHook、PermissionCache、InlineDialogManager、ContentRulesManager、BootReceiver、PermissionProvider、PermissionStorage、PermissionDialogActivity、MainActivity、WriteRulesDetailActivity、ReadRulesDetailActivity

### 查看方式
LSPosed Manager → 日志页面

### 最终状态
- 全项目 0 处 `import android.util.Log`（包括 MainActivity 的残留 import 已清理）
- XLog 内部仍用 `android.util.Log.getStackTraceString(t)` 格式化异常堆栈（仅限 XLog 内部）
- App 侧使用 `compileOnly` 引入 XposedBridgeAPI-82.jar，编译通过，运行时由 LSPosed 注入提供

### ⚠️ 致命 Bug：App 进程崩溃
**问题**：XLog.java 直接 `import de.robv.android.xposed.XposedBridge` 并在静态方法中直接调用。App 进程启动时 `PermissionProvider.onCreate()` → `XLog.i()` → JVM 尝试解析 `XposedBridge` 类 → `NoClassDefFoundError`（compileOnly 依赖运行时不存在）→ App 闪退。
**修复**：XLog 改为反射调用 `XposedBridge.log()`。`static` 块中 `Class.forName()` 检测类是否可用，将 `Method` 引用缓存到 `sLogMethod`。调用时通过 `sLogMethod.invoke()` 间接调用，完全避免直接类引用。App 进程中 `sLogMethod == null`，自动 fallback 到 `android.util.Log`。

## 2026-05-04 第五次修复：开机自启动失败 + 日志写入失败

### 问题1：开机自启动失败

**现象**：用户反馈"开机自启动还是失败了"，日志显示 `writeBlockSet.size=0`。

**根本原因**：时序竞争问题。
- Hook 侧在 `延迟5s` 和 `延迟8s` 才注册广播接收器
- BootReceiver 立即发第一次广播 + 3秒后发第二次（已在第三次修复中改为 15s + 18s）
- **但是**：`BootReceiver.java` 中的 `SECOND_BROADCAST_DELAY_MS` 仍然是 3000L（3秒），第一次广播延迟是 0（立即发送）

**修复（BootReceiver.java）**：
- 新增 `FIRST_BROADCAST_DELAY_MS = 15000L`（15秒），确保 Hook 侧广播接收器已注册
- 保留 `SECOND_BROADCAST_DELAY_MS = 3000L`（15s + 3s = 18s 发第二次）
- 修改 `onReceive()` 中的线程逻辑，先 sleep 15s 再发第一次广播

**新时序**：
```
t=0:    收到开机广播
t=0~15s: 等待 Hook 侧注册广播接收器（Hook 在 5s 和 8s 注册）
t=15s:   BootReceiver 第一次发广播 → Hook 侧已注册，收到配置
t=18s:   BootReceiver 第二次发广播（兜底）
```

### 问题2：日志写入失败

**现象**：放行或拦截后，日志写入失败。
```
[E][ClipboardGuard.Provider] 写入日志失败: Given calling package android does not match caller's uid 10546
```

**根本原因**：Binder 身份未清除。
- 微信（uid 10546）调用 `setPrimaryClip`，这个 Binder 调用到达 system_server
- Hook 拦截后调用 `writeLog()` → `PermissionProvider.writeLog()` → `context.getContentResolver().insert(uri, cv)`
- 这个新的 Binder 调用会携带原始调用者的身份（微信，uid 10546）
- 但是 system_server 的 package 是 "android"，导致 uid（10546）和 package（android）不匹配

**修复（WriteHook.java）**：
在 `writeLog()` 方法中，调用 `PermissionProvider.writeLog()` 之前，使用 `Binder.clearCallingIdentity()` 清除 Binder 身份，调用后恢复。

```java
private static void writeLog(Context ctx, String pkgName, String action, String content) {
    // ...
    long identity = Binder.clearCallingIdentity();
    try {
        PermissionProvider.writeLog(ctx, pkgName, action, content);
    } finally {
        Binder.restoreCallingIdentity(identity);
    }
}
```

这样，当 `context.getContentResolver().insert()` 发起跨进程调用时，会使用 system_server 自己的身份（uid 1000，package "android"），uid 和 package 匹配，权限检查通过。

### 修改文件
- `BootReceiver.java`：增加首次广播延迟到 15 秒
- `WriteHook.java`：`writeLog()` 方法添加 Binder 身份清除/恢复

## 2026-05-04 第六次修复：移除数据库日志功能

### 动机
用户反馈"写入日志失败"错误持续出现（`Given calling package android does not match caller's uid xxx`），
虽然之前已在 `WriteHook.writeLog()` 中添加了 `Binder.clearCallingIdentity()`，但问题仍然存在。

### 用户决策
不再保存日志到数据库，只保留 XLog（XposedBridge.log）输出到 LSPosed Manager。

### 修改内容

**WriteHook.java**：
- `writeLog()` 方法简化为直接调用 `XLog.i()` 输出到 LSPosed，不再调用 `PermissionProvider.writeLog()`

**PermissionProvider.java**（大量清理）：
- 删除 `URI_LOG_ALL`、`URI_LOG_INSERT`、`URI_LOG_CLEAR` 常量和 UriMatcher 注册
- 删除 `COL_ACTION`、`COL_CONTENT`、`COL_TIMESTAMP` 常量
- 删除 `clipboard_log` 表的 CREATE 语句
- 删除 `query()` 中的 `URI_LOG_ALL` 处理
- 删除 `insert()` 中的 `URI_LOG_INSERT` 处理
- 删除 `delete()` 中的 `URI_LOG_CLEAR` 处理
- 删除 `call()` 中的 `"writeLog"` case
- 删除 `writeLog()` 静态方法
- 删除 `getLogs()` 静态方法
- 删除 `clearLogs()` 静态方法
- DB_VERSION 升级到 3，`onUpgrade` 中 DROP 掉 `clipboard_log` 表
