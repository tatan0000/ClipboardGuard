# 2026-04-06 开发日志

## 上午：修复权限读取错误导致始终放行的问题

### 问题分析（来自日志）
```
ContentProvider查询失败: Given calling package android does not match caller's uid 10131
ContextImpl: Failed to ensure /data/user/0/.../shared_prefs: mkdir failed: EACCES
ClipboardGuard.Storage: 从SharedPreferences读取: com.android.chrome = 1  ← 读到放行！
```

### 根本原因（三个）
1. **主界面保存只调用 `PermissionProvider.savePermission()`**，只写 ContentProvider(SQLite)，没有写 SharedPreferences
2. **`DEFAULT_PERMISSION = PERMISSION_IGNORE`**，Hook 端未配置的应用默认放行
3. **`isModuleProcess()` 限制了 SharedPreferences 读写**，system_server 进程被跳过

### 修复内容
1. `MainActivity.saveChanges()` 改为调用 `PermissionStorage.setPermission()`（同时写三处）
2. `Hook.java` 的 `DEFAULT_PERMISSION` 改为 `PERMISSION_BLOCK`（默认拦截）
3. `PermissionStorage.getPrefs()` 改用 `MODE_WORLD_READABLE`，让其他进程可读
4. `PermissionStorage.setPermission()` 去掉 `isModuleProcess` 限制，任何进程都写 SharedPreferences
5. `PermissionStorage.getPermission()` 去掉 `isModuleProcess` 限制，任何进程都尝试读 SharedPreferences

### 预期行为
- 主界面勾选拦截 → 保存到 ContentProvider + SharedPreferences + 系统文件
- system_server Hook 读取：ContentProvider 失败 → 系统文件失败 → SharedPreferences 成功读到 BLOCK(0)
- 未配置的应用默认 BLOCK → 弹窗询问

## 上午第二轮：ContentProvider call()方法修复（SELinux完全封堵问题）

### 新问题
所有存储路径被 SELinux 完全封堵：
- ContentProvider query()：`calling package android does not match caller's uid 10131`（Binder包名校验）
- shared_prefs：`mkdir failed: EACCES`
- files/：`mkdir failed: EACCES`

### 根本原因
system_server（uid=1000）无法访问 `/data/user/0/com.android.clipboardguard/` 的任何子目录。
`ContentResolver.query()` 会校验调用方包名和uid是否匹配，android包名对应uid=1000但实际调用uid=10131（错误）。

### 修复方案：ContentProvider.call() 方法
`call()` 方法不经过 Binder 包名/uid 绑定校验，可以直接跨进程调用。

**PermissionProvider.java 修改**：
1. 添加 `call()` 方法实现（CALL_METHOD_GET/SET），内部用 `Binder.clearCallingIdentity()` 
2. `queryPermission()` 静态方法改用 `ContentResolver.call()` 而非 `query()`
3. `savePermission()` 静态方法改用 `ContentResolver.call()` 而非 `insert()`

**AndroidManifest.xml 修改**：
- 移除 `android:multiprocess="true"`（确保Provider只在模块进程有唯一DB实例）

### 预期效果
system_server 调用 `call("getPermission", null, bundle)` → Provider接收 → DB查询 → 返回Bundle

## 上午第三轮：真正根因定位 - Binder 调用者身份问题

### 新一轮日志分析
```
ClipboardGuard.Provider  E  查询权限失败: Given calling package android does not match caller's uid 10131
```
uid=10131 是 Chrome，不是 system_server(uid=1000)！

### 真正根因
Hook 在 system_server 的 Binder 线程里执行（处理来自 Chrome 的 IPC 调用）。
此时 `Binder.getCallingUid()` 返回的是**远端调用者 Chrome 的 uid=10131**（这是 Binder 线程的特性）。

所以当 Hook 代码里调用 `ContentResolver.call()` 时：
- ContentResolver 从 Binder 获取 callingUid = 10131（Chrome）
- ContentResolver 填写 callingPackage = "android"（因为 context 是 system_server）
- ContentProvider 服务端检查：android 对应 uid=1000，但实际 callingUid=10131 → 不匹配 → 报错！

### 修复方案（最终版，极简）
在读取权限前调用 `Binder.clearCallingIdentity()`：
```java
long identity = Binder.clearCallingIdentity();
try {
    savedPerm = directQueryPermission(systemContext, pkgName);
    // fallback...
} finally {
    Binder.restoreCallingIdentity(identity);
}
```
`clearCallingIdentity()` 把 Binder 调用者 uid 重置为本进程 uid=1000（android），与 callingPackage 完全匹配。

### 相关代码变更
- `Hook.java`：`beforeHookedMethod` 中读权限前加 `clearCallingIdentity()`
- `Hook.java`：`directQueryPermission()` 方法改为直接用 `ContentResolver.call()`（不再需要反射绕过）
- `Hook.java`：删除已不再使用的 `getModuleContext()` 方法
- `Hook.java`：新增 `readPermissionFromFile()` 作为最终 fallback（直接读 SQLite 文件）

## 下午：防抖逻辑修复 + 防崩溃

### 问题：没有防抖了吗？
从日志分析发现防抖逻辑在工作，但时间太短：
- 第一次操作 16:13:35 → 用户允许 16:13:39（间隔3.5秒）
- 第二次操作 16:13:39 → 又弹窗（因为 3.5秒 > 1.5秒防抖）

### 修复
将防抖时间改为1.5秒，且防抖从**用户选择完成**时开始计时：
```java
private static final long DEBOUNCE_MS = 3_000;  // 防抖3秒
private static final Map<String, Long> sLastDecisionTime = new HashMap<>();  // 用户选择完成时间

// 防抖检查：检查用户选择完成时间
Long lastDecision = sLastDecisionTime.get(pkgName);
if (lastDecision != null && now - lastDecision < DEBOUNCE_MS) {
    // 防抖期间，应用上次选择
}

// askUser() 返回后更新sLastDecisionTime
sLastDecisionTime.put(pkgName, now);
```

### 根因
`queryPendingResult()` 使用 `ContentResolver.call()` 时，某些 Android 11 内核上 Binder 事务异常（`Outgoing transactions must be FLAG_ONEWAY`），导致无法读取到最新的 pending 结果。

### 修复
1. **改用 `resolver.query()`** 替代 `resolver.call()`，更稳定
2. **优化防抖逻辑优先级**：
   - 首先尝试从 pending 表读取
   - 如果没有，回退检查内存缓存（`sLastUserDecision`）
   - 确保即使 Provider 未就绪也能用到最新决策

### 问题 2：弹窗进程崩溃重启
日志显示模块进程被系统 kill 后（`Killing 5012:com.android.clipboardguard`），`DialogLaunchReceiver` 仍尝试启动 Activity 导致 `DeadObjectException`。

### 修复
`DialogLaunchReceiver.java` 增加进程存活检查：
1. `onReceive()` 入口检查模块进程是否存活
2. 延迟启动前二次检查进程状态
3. 进程已死亡则丢弃弹窗请求，避免崩溃
