## 正则广告过滤功能重构（19:38）

**需求澄清**：
- 正则不是识别敏感信息（身份证/手机号）
- 而是过滤垃圾广告：某些 App 自动把推广文案/邀请码写入剪贴板
- 默认规则：**不要**，完全由用户自定义
- 后续计划：写正则规则配置 UI（开关 + 规则增删改）

**最终拦截流程（双层过滤）**：
1. 包名在白名单（isIgnored=true）→ 直接放行
2. 包名在拦截列表（isIgnored=false）→ 执行正则匹配：
   - 规则为空（用户未配置）→ 直接弹窗（兜底，让用户感知 App 在写剪贴板）
   - 规则非空 + 内容**未命中** → 正常内容，直接放行（减少误扰）
   - 规则非空 + 内容**命中** → 弹窗询问用户

**本次修改文件**：
- `ContentRulesManager.java`：
  - 语义改为"广告内容过滤"
  - 去掉所有默认规则（身份证/手机号/邮箱）
  - 文件不存在/解析失败时规则列表为空（不拦截）
  - `matchesSensitiveContent()` → `matchesAdContent()`
  - 新增 `getRulesEmpty()` 方法
- `Hook.java`：加回步骤2正则判断，逻辑同上
- `PermissionCache.java`：loadIgnoreSet() 中加回 `ContentRulesManager.loadRules()`

## 开机后第一次复制不弹窗问题修复（21:03）

**问题根因**：
1. 开机时 `ActivityThread.getApplication()` 可能返回 null
2. `getSystemServerContextStatic()` 返回 null → PermissionCache 初始化失败（sLoaded=false）
3. `getCallingPackageName()` 返回 null → 代码提前 return，直接放行
4. `getSystemServerContext()` 返回 null → InlineDialogManager 无法弹窗

**修复方案**：
1. `PermissionCache.java`：
   - 新增开机完成广播接收器（`ACTION_BOOT_COMPLETED`）
   - 开机后延迟 5 秒重新初始化（等待 system_server 完全就绪）
   - 新增 `getSystemServerContextSafe()` 带重试的 Context 获取方法
   - 新增 `refreshReceiverInternal()` 重新注册刷新接收器

2. `Hook.java`：
   - `getSystemServerContextStatic()`：最多重试 10 次，每次间隔 500ms
   - `beforeHookedMethod()`：获取包名和 Context 都添加重试机制（最多 5 次，每次 100ms）
   - 新增 `getCallingPackageNameWithRetry()` 和 `getSystemServerContextWithRetry()` 方法

**编译结果**：BUILD SUCCESSFUL

## FileObserver 替换广播（21:15）

**改动原因**：广播有时序风险（开机时可能丢失），FileObserver 更可靠

**改动内容**：
1. `PermissionCache.java`：
   - 新增 `FileObserver` 监听配置文件变化（主刷新机制）
   - 监听 `CLOSE_WRITE | MODIFY` 事件
   - 配置文件变化时立即刷新缓存
   - 保留广播 + 30s 兜底作为双重保障

**双重保障机制**：
```
1. FileObserver（主）：文件变化 → 立即刷新
2. 30s 兜底（备）：即使 FileObserver 失效，30秒内必然刷新一次
3. 广播（备）：App 保存后发广播（可选保留）
```

**优点**：
- 无广播时序问题
- 实时感知文件变化
- 不依赖 App 进程
- 无需保活

**编译结果**：BUILD SUCCESSFUL

## 开机自动初始化 Hook（21:17）

**改动原因**：Hook 加载时可能 Context 获取失败，导致 PermissionCache 未初始化

**改动内容**：
1. `Hook.java` 新增 `ensureInitialized()` 方法
2. `beforeHookedMethod()` 开头调用 `ensureInitialized()`
3. 如果 PermissionCache 未加载，立即尝试初始化（最多重试 10 次，每次 500ms）

**流程对比**：
```
之前：
  开机 → Xposed Hook 加载 → getSystemServerContextStatic() 失败 → 未初始化
                                                              ↓
                                                       依赖 App 启动才能初始化

现在：
  开机 → Xposed Hook 加载 → try → getSystemServerContextStatic()
                                           ↓ 失败
  ClipboardService.setPrimaryClip() 被调用
                                           ↓
  beforeHookedMethod() → ensureInitialized() → 初始化成功
```

**优点**：
- 不需要 App 启动
- 开机后第一次写剪贴板时自动初始化
- 重试机制保证初始化成功

**编译结果**：BUILD SUCCESSFUL

## 开机第一次复制的保守拦截策略（21:19）

**问题根因**：
- `getCallingPackageNameWithRetry()` 返回 null 时直接 return 放行
- 如果是普通 App（不是核心包）被放行，剪贴板内容会被复制（危险）

**修复方案**：
1. `Hook.java`：`beforeHookedMethod()` 重构双重兜底逻辑
   - 包名获取失败 → 保守拦截（不弹窗不阻断，只记录日志）
   - Context 获取失败 → 保守拦截（不弹窗不阻断）
   - 只有包名和 Context 都获取成功时才正常弹窗

2. `Hook.java`：`ensureInitialized()` 增强
   - 强制等待初始化，最多 120 次 × 500ms = 60 秒
   - 确保开机后第一次复制能在 60 秒内等到初始化完成

3. `PermissionCache.java`：`loadIgnoreSet()` 增强
   - 确保只有真正加载成功才设置 `sLoaded = true`
   - 失败时 `sLoaded = false`（避免误判为已加载）

**保守策略对比**：
| 情况 | 之前 | 现在 |
|------|------|------|
| 包名获取失败 | 放行（危险） | 保守拦截（只记录） |
| Context 获取失败 | 放行 | 保守拦截（只记录） |
| 初始化超时 | 使用 sLoaded=false | 60 秒强制重试 |

**编译结果**：BUILD SUCCESSFUL

## 开机初始化重试策略（21:28）

**改动原因**：开机时初始化失败后一直重试不合理，应该有明确的停止条件

**改动内容** - `Hook.java`：
1. `hookClipboardService()` 重构延迟初始化逻辑
   - 延迟 10 秒后第一次尝试初始化
   - 失败则等待 15 秒后重试
   - 再失败则停止尝试（不再无限循环）
   - 成功则立即停止

2. 新增 `tryInitialize()` 辅助方法
   - 封装初始化逻辑
   - 返回 true=成功，false=失败

**完整初始化流程**：
```
开机 → Hook 加载
           ↓
      延迟 10 秒 → tryInitialize()
           ↓ 失败
      等待 15 秒 → tryInitialize()
           ↓ 失败
      停止尝试（需重启或模块更新）

或者：
开机 → Hook 加载
           ↓
      延迟 10 秒 → tryInitialize() → 成功
           ↓
      就绪
```
